# Dorka delivery forecast

## Purpose and status

This forecast turns the functioning-version goal into an ordered delivery plan. It reflects
`feat/dorka-computers` through `1a3755ba6` and the evidence listed below. A checked item means the
repository contains both implementation and named verification evidence, or the functioning-version
goal records a completed live check.

Current verdict: the retained shell and native campaigns prove substantial lifecycle, isolation, UI,
and recovery mechanics, but they use the old placement: the provider process and skill/MCP resolution
run inside the Computer. The corrected model runs Agent/provider processes, provider credentials, and
global skills/MCP on the control plane. It keeps workspace, packages, Git/SSH identity, environment,
secrets, and desktop on the selected Computer behind a managed execution adapter.

The ownership correction is the controlled-beta blocker. Existing native and Electron evidence remains
valid evidence for the old placement mechanics. It is not acceptance of corrected process placement,
and the code is not complete until the new boundary has focused and native end-to-end proof.

## Execution flow

```text
Desktop/mobile client
  -> authenticated dorkad RPC
  -> create Run with agentId + computerId
  -> launch provider process + PTY on control plane
  -> load provider credentials + global skills/MCP on control plane
  -> managed execution adapter
  -> selected Computer workspace/packages/Git+SSH/env/secrets/desktop
  -> stream terminal, status, diff, review, and questions back to clients
```

The launch correction is in progress. Run records now distinguish provider-process placement from
the selected Computer target. The Server can project a private, generation-fenced SSH bridge and a
managed Pi extension can route file and shell tools through it without local fallback. The remaining
work is to compose that extension into the Server-local PTY launch, move global requirements to the
Server, and recompose exact exit/recovery ownership without weakening Computer isolation.

## Known risks

- **Incorrect provider placement:** current code launches the provider inside the Computer. The corrected
  boundary keeps provider process/credentials and global skills/MCP on the control plane, while every
  workspace operation crosses the managed execution adapter. This blocks controlled beta.
- **False liveness:** a disconnected client or Server does not prove a Computer process exited.
  Preserve `live` / `unverifiable` / `exited` semantics through Run status.
- **Engine authority:** the mounted container-engine socket can control everything owned by its
  service account. Rootless operation reduces impact but is not a security boundary by itself.
- **Image availability:** the pinned Selkies base is currently `linux/amd64`; arm64 development may
  require emulation and can hide native-Linux defects.
- **SSH host identity:** the dedicated `/etc/ssh` volume preserves host keys across normal
  replacement. Recovery that loses this volume must still establish an explicit target generation;
  silently accepting a changed key is not allowed.
- **Wire compatibility:** clients and Servers update independently. Add optional RPC fields and
  capability-negotiate new stream behavior.
- **Premount filesystem identity:** exact string allowlisting does not yet canonicalize symlinks on
  the execution host. Treat allowlisted paths and ancestors as operator-owned until canonical-path
  validation lands.
- **Ordinary environment is not a secret channel:** values currently cross RPC and engine argv.
  The UI labels them non-secret; add secret references before accepting confidential values.
- **Review portability:** Computer-local review must support GitLab and other providers, not only
  GitHub credentials and terminology.
- **Exit-fixture ownership:** the fast reproducer proved interactive shells ignore `SIGTERM`; the
  fixture uses `SIGKILL` and the native release gate now proves exact-generation and exact-incarnation
  replay. Keep those assertions unchanged.
- **Validation cost:** rebuilding and reprovisioning Selkies for every relay change hides the signal.
  Keep immutable images only when source/input labels match, always use fresh runtime state, and run
  the clean campaign once after focused checks pass.
- **Scope creep:** desktop streaming, marketplace work, and broad legacy deletion can delay the P0
  launch path. Keep them out of Now.

## Milestone gates

1. **M0 — Baseline (complete):** retained shell launches; durable Agent/Computer control-plane
   seams exist; focused checks and a limited live smoke are recorded.
2. **M1 — Transitional native loop (complete):** native graphical startup, Computer-local provider
   launch, durable identity, terminal output, Run Diff/Review, Git identity, Server replacement, and
   post-outage completion are proved as old-placement mechanics.
3. **M2 — Corrected multi-Computer beta (blocked):** move provider launch, provider credentials, and
   global skills/MCP to the control plane; prove managed Computer execution and ownership isolation;
   then rerun placement, move, reconnect, and mixed-version gates.
4. **M3 — Desktop and production hardening (Later):** scoped desktop access and operational controls
   satisfy security, recovery, and upgrade gates.

## Update protocol

Update this document in the same change that alters milestone scope or status:

1. Rebase the snapshot commit in **Purpose and status** to the reviewed code revision.
2. Mark an item complete only with a code path plus an automated test, or a named manual/E2E run
   with date, command, platform, and durable artifact.
3. Move incomplete work between Now/Next/Later instead of checking it optimistically.
4. Record new blockers in **Known risks** and add their dependency to the backlog row.
5. Revise forecast ranges when a dependency slips or measured work invalidates an assumption.
6. Never infer completion from implementation presence alone, and never treat loss of remote contact
   as proof that execution stopped.
